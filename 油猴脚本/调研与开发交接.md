# LeetCode 油猴辅助：调研与开发交接

> 调研日期：2026-07-24  
> 当前状态：纯油猴方案可行，尚未开始编写脚本。下一步需要在 Windows 原生环境中连接用户当前的 Chrome，确认 LeetCode 编辑器的实际写入接口。

## 1. 已确认的项目边界

这是一个准备从当前仓库中单独移出的独立油猴项目。后续开发必须遵守：

- 运行时不依赖现有 `Assistant` WPF 程序，也不依赖它的本地服务、热键、设置或 Windows 凭据。
- DeepSeek 等大模型的 API Key 可以保存在油猴脚本自己的存储中。
- 不需要为了 API Key 或快捷键开发浏览器扩展。
- 主要运行环境是 Windows 上的 Chrome 和 Tampermonkey，目标网站首先是 `https://leetcode.cn/problems/*`。
- 用户原需求中的 `atl` 按笔误理解为 `alt`。
- 快捷键不必保留 `Win+Alt+S/A/D`。只要不与 Chrome、LeetCode、现有 Assistant 和常用 Windows 操作冲突，用户可以配合实机测试并调整。
- 用户会把整个 `油猴脚本/` 文件夹移到 Windows 原生目录，并在新 session 中继续开发，所以本文件需要作为完整上下文入口。

原始需求见同目录的 `油猴-需求.md`。

## 2. 需求整理

### 2.1 识题与 AI

- 功能开启时，识别当前 LeetCode 题目并请求 AI 生成正确答案。
- LeetCode 站内切换到另一题时，应识别 URL/slug 变化并自动重新处理。
- 提供一个“强制重新识别”快捷键，即使 slug 没变也重新抓题并请求 AI。
- 新请求开始后取消或废弃旧请求；旧题的迟到结果不得覆盖当前题目。
- 第一版不负责自动点击“运行”或“提交”。

### 2.2 两个 2×2 状态灯

页面左上角放置两个不显眼的 2 CSS 像素见方状态灯：

第一个灯表示主流程：

- 灰色：功能关闭
- 黄色：正在读取题目或等待 AI
- 绿色：答案已准备好
- 红色：当前题目读取、配置、网络、AI 解析或编辑器操作发生错误

第二个灯表示按键劫持：

- 灰色：关闭
- 绿色：开启

建议使用固定定位、最高 `z-index`、`pointer-events: none`，两个灯之间保留约 2px 间隔。2px 指 CSS 像素，在高 DPI 屏幕上不一定等于两个物理像素。

### 2.3 按键劫持

- AI 答案准备好且劫持功能开启后，用户每按下一次普通按键，就在当前 LeetCode 代码编辑器光标处写入答案的下一个字符。
- 用户实际按下的字符不进入编辑器。
- 答案的换行和缩进也属于要依次插入的内容。
- 修饰键本身、功能快捷键的最后一个按键、IME 组合输入期间的事件和 `keydown.repeat` 不应消耗答案字符。
- 功能快捷键必须在劫持开启时仍可正常关闭劫持或关闭总功能。
- 建议按 Unicode code point 拆分答案（例如 `[...answer]`），不要按 UTF-16 单元拆分代理对。
- 页面切题、重新识别、AI 出错或答案上下文失效时，立即停止旧答案的劫持。

尚需用户最终确认的交互细节：

- 答案全部输入完后，是自动关闭劫持，还是保持绿色但不再吞按键。
- 识别成功后是在当前光标处开始插入，还是先清空/选择 LeetCode 默认模板。SQL 题通常可以从默认注释后开始，但普通算法题往往需要保留并填写函数模板。
- 第一版是否只支持数据库/SQL 题，还是同时支持 LeetCode 的所有语言题。当前示例是 MySQL 题，但原始需求没有明确限制。

## 3. 可行性结论

纯油猴脚本可以完成需求主体，不需要浏览器扩展：

| 能力 | 纯油猴结论 | 实现方向 |
|---|---|---|
| 读取当前题目 | 可行 | 解析页面的 `#__NEXT_DATA__`，必要时回退到 DOM |
| 监听站内切题 | 可行 | 观察 `location.href`/slug，变化后重新抓取 |
| 请求 DeepSeek | 可行 | `GM_xmlhttpRequest`/`GM.xmlHttpRequest` + `@connect` |
| 保存 Key 和设置 | 可行 | `GM_setValue`/`GM_getValue` |
| 两个状态灯 | 可行 | 注入固定定位 DOM/CSS |
| 捕获页面按键 | 可行 | `window` 捕获阶段 `keydown` |
| 向 Monaco 逐字符写入 | 原理可行，待实机确认最佳接口 | Monaco model 优先，隐藏 textarea/input 作为回退 |
| `Win+Alt` 系统级热键 | 不保证，也不再要求 | 改用页面内组合键 |

油猴和普通网页脚本都不能注册真正可靠的 Windows 全局热键；Chrome 扩展的 `commands` API 在 Windows 上也不支持 `Win` 修饰键。因此仅为了原来的 `Win+Alt` 改做扩展没有价值。

## 4. 已验证的 LeetCode 实际题目数据

调研页面：

`https://leetcode.cn/problems/article-views-i/`

对该页面实际返回的 HTML 进行了解析。页面的：

```html
<script id="__NEXT_DATA__" type="application/json">...</script>
```

包含完整题目数据。当前可用的数据路径是：

```text
props.pageProps.dehydratedState.queries[*].state.data.question
```

应遍历 `queries`，选择存在 `state.data.question` 且 slug 与当前 URL 匹配的项，不要把数组下标 `1` 写死。

在“1148. 文章浏览 I”页面实际读取到：

```text
questionFrontendId: 1148
title: Article Views I
translatedTitle: 文章浏览 I
titleSlug: article-views-i
translatedContent: 1213 个字符
mysqlSchemas: 9 条语句
codeSnippets: 5 种语言
```

`codeSnippets` 包含：

- MySQL
- MS SQL Server
- PostgreSQL
- Oracle
- Pandas

重要字段建议读取：

```text
questionId
questionFrontendId
title
translatedTitle
titleSlug
content
translatedContent
mysqlSchemas
codeSnippets
topicTags
difficulty
```

### 4.1 推荐抓取策略

1. 首次进入题目时，先解析当前文档里的 `#__NEXT_DATA__`。
2. LeetCode 是 SPA。站内切题后，原文档中的 `#__NEXT_DATA__` 可能仍是首次加载的数据，不能默认它会随路由更新。
3. 检测到 slug 改变后，请求当前新题目的完整 URL，使用 `DOMParser` 解析返回 HTML 中的新 `#__NEXT_DATA__`。
4. 若 Next 数据结构变化或找不到题目，再回退到当前可见题面 DOM。
5. 用 `slug + 题面内容 + 当前语言/模板` 生成上下文标识。请求完成后再次核对标识，避免迟到答案用于错误题目。

这种方式比依赖题面面板的 CSS class 稳定，因为 LeetCode 的动态布局、压缩 class 名和面板位置可能变化。

## 5. 推荐的纯油猴架构

建议拆成以下逻辑模块，即使第一版仍放在一个 `.user.js` 文件中，也保持函数职责清晰：

```text
AppState
├── SettingsStore        API Key、模型、Base URL、快捷键和开关
├── RouteWatcher         观察 URL/slug 变化
├── QuestionExtractor    读取和规范化 Next 数据/DOM
├── AiClient             请求、取消、JSON 解析和错误处理
├── StatusLights         两个 2×2 状态灯
├── EditorAdapter        定位编辑器并插入一个字符
└── KeyboardHijacker     快捷键与逐字符消费
```

### 5.1 建议的用户脚本元数据

具体 `@grant` 名称应在实现时按实际同步版或异步版 API 统一：

```javascript
// @match        https://leetcode.cn/problems/*
// @connect      api.deepseek.com
// @grant        GM_getValue
// @grant        GM_setValue
// @grant        GM_xmlhttpRequest
// @grant        GM_registerMenuCommand
// @grant        GM_addStyle
// @grant        unsafeWindow
// @run-at       document-start
```

如果 Base URL 允许用户修改，`@connect` 不能在运行时动态扩大权限。第一版最好只支持明确列出的官方域名，避免使用过宽的 `@connect *`。

### 5.2 状态与持久化建议

建议持久化：

- API Key
- API Base URL
- 模型名
- 三个快捷键
- 总功能开关
- 用户选择的语言或提示词配置

建议只保存在当前页面内存中：

- 当前题目全文
- AI 返回的完整答案
- 当前答案字符下标
- 当前错误详情
- 在途请求对象和请求序号

为避免刷新页面后意外吞键，按键劫持开关建议每次页面加载默认关闭，不从上次会话恢复。

## 6. AI 请求设计

### 6.1 输入上下文

发送给模型的内容至少包含：

- 题号、中文/英文标题和 slug
- 中文题面优先，缺失时使用英文题面
- SQL Schema（如果有）
- 当前选择的语言
- 对应的 starter code
- 明确要求只返回可直接放进 LeetCode 编辑器的完整答案

不要只发送页面可见的短片段，也不要把 LeetCode 登录 Cookie 发送给模型域名。

### 6.2 返回协议

建议要求严格 JSON，例如：

```json
{
  "answer": "SELECT ...;",
  "language": "mysql"
}
```

本地需要：

- 验证 `answer` 是非空字符串。
- 去除模型偶尔附带的 Markdown 代码围栏。
- 保留答案内部换行和缩进。
- 不把 AI 解释文字混入编辑器答案。
- API 请求出错、超时、JSON 无法解析或返回空答案时设为红灯。

### 6.3 请求一致性

- 每次识别分配递增 `requestId` 或使用 `AbortController`/油猴请求的 `abort()`。
- 切题、关闭总功能和手动重跑时取消旧请求。
- 写入 `currentAnswer` 前再次校验当前 slug、内容标识、语言和请求序号。
- 不允许旧答案在新页面上继续逐字符输出。

## 7. Monaco 编辑器写入方案

这一部分尚未在用户当前登录的 Chrome 页面上验证，是下一 session 最重要的实机调研。

### 7.1 首选：Monaco model/editor API

检查：

```javascript
unsafeWindow.monaco
unsafeWindow.monaco?.editor
unsafeWindow.monaco?.editor?.getModels?.()
unsafeWindow.monaco?.editor?.getEditors?.()
```

如果页面暴露 Monaco：

- 找到当前可见且拥有焦点的编辑器实例。
- 使用编辑器的 `executeEdits` 在当前 selection/caret 插入一个字符。
- 更新 selection，保证下一次继续从新光标写入。
- 为每次物理按键执行一次 edit，保留合理的撤销行为。
- 如果页面有多个 Monaco model，不要盲目使用 `getModels()[0]`；测试用例编辑器、控制台或隐藏 tab 也可能创建 model。

### 7.2 回退：Monaco 隐藏输入框

检查类似：

```text
.monaco-editor
.monaco-editor textarea.inputarea
textarea[aria-label*="代码编辑器"]
```

可能的回退方式：

1. 聚焦当前可见 Monaco 的隐藏 textarea。
2. 尝试 `document.execCommand("insertText", false, character)`。
3. 若无效，再测试更新 textarea value/selection 后派发合适的 `beforeinput`/`input`。

仅创建合成 `KeyboardEvent` 通常不会触发浏览器的默认文字插入，因为事件不是可信用户输入，不能把它当作唯一写入方案。

### 7.3 不推荐方案

- 不优先使用剪贴板逐字符粘贴，避免破坏用户剪贴板。
- 不依赖压缩后的 React class 名。
- 不把答案直接一次性覆盖整个 model；原需求要求一个物理按键对应一个答案字符。
- 不通过模拟“提交”按钮完成题目。

## 8. 快捷键方案

建议第一版默认：

| 功能 | 默认快捷键 |
|---|---|
| 总开关 | `Ctrl+Alt+7` |
| 强制重新识别 | `Ctrl+Alt+8` |
| 开启/关闭按键劫持 | `Ctrl+Alt+9` |

选择数字是为了避开当前 Assistant 已使用的 `Ctrl+Alt+S/A`，也避开 Chrome 常见的字母快捷键。最终仍需在用户 Windows、输入法和 LeetCode 编辑器中实测。

实现时使用 `KeyboardEvent.code`（`Digit7`/`Digit8`/`Digit9`）识别物理键位，并在 `window` 的捕获阶段注册监听。处理成功后调用：

```javascript
event.preventDefault();
event.stopPropagation();
event.stopImmediatePropagation();
```

按键判断顺序：

1. 先识别三个功能快捷键。
2. 再判断是否应该劫持普通按键。
3. 排除 `Control`、`Alt`、`Shift`、`Meta` 等单独修饰键。
4. 排除 `event.repeat` 和 `event.isComposing`。
5. 每个合格 `keydown` 只消费一个答案字符。

还应注册 Tampermonkey 菜单作为兜底：

- 开启/关闭功能
- 重新识别当前题
- 开启/关闭按键劫持
- 配置 API
- 修改快捷键或恢复默认值

## 9. API Key 与隐私

用户已经接受把 API Key 保存到油猴自身存储中，因此不需要 Windows 凭据管理器。

仍建议：

- 不把真实 Key 写死在 `.user.js` 源码或提交到 Git。
- 用油猴菜单打开脚本注入的 `<input type="password">` 设置框，再调用 `GM_setValue`。
- 不在控制台、错误灯 tooltip 或网络错误文本中输出 Authorization Header。
- `@match` 只覆盖 LeetCode 题目页。
- `@connect` 只覆盖实际模型域名。
- 明确提示用户：题面、Schema、语言模板和必要的当前代码会发送给配置的 AI 服务。
- 油猴存储不是 Windows 凭据管理器，安全级别不同；这是用户已明确接受的独立项目取舍。

## 11. 新 session 的实机检查清单

连接到用户 Chrome 后，先只读检查：

1. 找到 `leetcode.cn/problems/...` 当前标签页。
2. 记录当前 URL、标题和 slug。
3. 检查当前 DOM 的 `#__NEXT_DATA__` 是否仍能找到本文件记录的题目字段。
4. 检查页面站内切题后的 URL 和 Next 数据是否同步更新。
5. 统计可见 `.monaco-editor`、`textarea.inputarea`、带编辑器 ARIA label 的元素。
6. 检查主页面世界是否存在 `window.monaco` 及可用 editor/model API。
7. 判断当前选中语言、当前 model 内容和可见 editor 的对应关系。
8. 安装一个临时捕获监听器，让用户实按候选快捷键，验证 Chrome、Windows、输入法和 LeetCode 是否会拦截。

完成只读检查后，再做受控写入测试：

1. 在用户确认可修改的编辑器内容中插入一个无害字符。
2. 验证光标位置、model 内容和 UI 是否同时更新。
3. 立即用编辑器 API或撤销恢复。
4. 分别测试普通字符、换行和缩进。
5. 再决定首选与回退 EditorAdapter。

用户已经表示可以配合快捷键和编辑器实测，但仍应先说明每次会改变什么。

## 13. 最低验收清单

- 在示例题 `article-views-i` 上正确读取中文题面、MySQL Schema 和 MySQL starter code。
- 页面打开或站内切题后能自动识别。
- 强制识别快捷键能取消旧请求并重新请求。
- 第一状态灯完整覆盖灰、黄、绿、红四种状态。
- 第二状态灯准确反映劫持开关。
- 劫持开启时，任意合格物理按键只插入答案的下一个字符。
- 长按键盘不会因系统自动重复而快速输出多个字符。
- 换行和缩进能正确进入 Monaco。
- 三个功能快捷键在劫持开启时仍能工作。
- 页面切题后旧答案立即失效。
- AI 迟到结果不会覆盖新题或新语言。
- 没有 API Key、网络失败、模型返回异常时显示红灯且不吞普通按键。
- 页面刷新后按键劫持默认关闭。
- 不自动运行或提交答案。
- API Key 不出现在源码、控制台或错误信息中。
